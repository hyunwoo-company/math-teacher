# 스캔 이미지 PDF(제본 부교재) 문제 추출 방안

작성일: 2026-08-09
상태: **조사 결과 + 제안. 아직 구현하지 않았다.**

## 1. 문제

`tmp/풍문고 부교재.pdf` 를 업로드해도 문항이 하나도 추출되지 않는다.

### 확인한 사실 (PyMuPDF 로 검사)

- 54페이지, PDF 1.4, 암호화 없음
- **54페이지 전체의 텍스트 합계가 0자다.** 텍스트 레이어가 아예 없다
- 각 페이지가 `/XObject /Subtype /Image /Filter [/DCTDecode]` 이미지 **1장**뿐
- 이미지 원본 3303×4671px, DeviceRGB. JPEG 헤더에 `Canon Inc` → Canon 스캐너 출력물
- 48MB 중 대부분이 이 JPEG 데이터
- 페이지를 렌더해 보면 사람이 읽기에는 충분히 선명하다. 다만 **스프링 제본 그림자**가
  오른쪽에 들어가 있고 페이지가 미세하게 기울어져 있다. 조판은 2단이다

### 왜 안 되는가

`core/extractor.py` 는 `page.get_text("dict")` 로 얻은 줄 좌표에서 문제 번호
(`^\s*(\d{1,2})\s*\.`)를 앵커로 잡아 2단을 좌/우로 나눠 자른다.

`image` 모드도 "**크롭 좌표는 텍스트 앵커로 정하고** 잘라낸 그림만 AI 에 보낸다" 는 뜻이지,
앵커 자체는 텍스트가 있어야 한다. 텍스트 0자 → 앵커 0개 → 문항 0개.

PUA 비율로 모드를 자동 판정하는 로직(`extractor.py:123`)도 분모가 0이라 무의미하다.

## 2. 제안 (A안) — OCR 로 텍스트 레이어를 깔고 기존 파이프라인을 그대로 쓴다

```
스캔 PDF ──► [텍스트 레이어 없음 감지] ──► OCR ──► 투명 텍스트 레이어 주입
                                                        │
                                    기존 extractor 앵커 탐지 ◄┘
                                                        │
                                    크롭은 종전대로 이미지로 잘라 AI 에 전달
```

**핵심은 OCR 결과를 AI 에 보내지 않는다는 것이다.** OCR 은 오로지 "몇 번 문제가 페이지
어디에 있는가" 를 알아내는 데만 쓴다. 실제로 AI 가 보는 것은 지금과 똑같이 잘라낸 이미지다.

그래서 수식 OCR 정확도가 낮아도 상관없다. 필요한 것은 `1.` `2.` `3.` 같은 **숫자와 마침표**
뿐이고, 이건 OCR 이 가장 잘하는 축에 든다.

### 왜 이 방식인가

| 방안 | 평가 |
|---|---|
| **A. OCR 텍스트 레이어 주입** | 기존 extractor 를 그대로 쓴다. 22문항 분할이 검증된 코드를 건드리지 않는다 |
| B. 이미지 처리로 직접 분할 | 외부 의존성이 없지만, 기울기·제본 그림자·2단 구분선 검출을 직접 튜닝해야 한다 |
| C. 페이지 통째로 AI 에 전달 | 가장 단순하지만 토큰 비용이 크고 문항 단위 관리(풀이 저장·오답노트)가 무너진다 |

A 를 권한다. `ARCHITECTURE.md` 8항의 "extractor 로직 재작성 금지" 와도 어긋나지 않는다.

## 3. 구현 스케치

### 3-1. 감지

업로드 시 텍스트 총량을 재고, 임계 미만이면 스캔본으로 본다.

```python
total_chars = sum(len(page.get_text().strip()) for page in doc)
is_scanned = total_chars < 50 * doc.page_count   # 페이지당 50자 미만
```

임계값은 실측으로 정한다. 이 파일은 0자라 어떤 값으로도 걸린다.

### 3-2. OCR

**미설치 상태다.** 이 PC에 `tesseract`, `pytesseract`, `ocrmypdf` 모두 없다
(`requirements.txt` 에도 없음). 도입하려면 아래가 필요하다.

- `tesseract` 바이너리 + `kor` 언어 데이터
- 파이썬 바인딩(`pytesseract`) 또는 `ocrmypdf`
- **k3s 컨테이너 이미지에도 넣어야 한다.** 배포는 hw-01 k3s 이므로 Dockerfile 변경이 따른다

두 갈래가 있다.

**(a) `ocrmypdf` 로 PDF 전체를 한 번에 처리**
- 투명 텍스트 레이어가 깔린 새 PDF 가 나온다. 이후 코드는 아무것도 몰라도 된다
- `--deskew` 로 기울기 보정, `--optimize` 로 용량 절감을 덤으로 얻는다
- 48MB · 54페이지면 수 분이 걸린다 → **업로드 동기 처리로는 무리다.** 작업 큐가 필요하다
  (`docs/superpowers/specs/2026-08-09-server-job-queue-design.md` 의 큐를 재사용할 수 있다)

**(b) `pytesseract` 로 앵커 좌표만 뽑기**
- 페이지 이미지를 렌더해 `image_to_data` 로 단어별 bbox 를 받고, `^\d{1,2}\.$` 패턴만 고른다
- PDF 를 다시 쓰지 않고 extractor 에 좌표를 직접 넘긴다 → 훨씬 빠르고 가볍다
- 대신 extractor 에 "앵커를 외부에서 주입받는" 경로를 새로 내야 한다

**추측**: (b) 가 이 용도에 맞다. 우리는 텍스트 레이어가 필요한 게 아니라 앵커 좌표만
필요하기 때문이다. 다만 어느 쪽이 실제로 22문항을 정확히 잡는지는 **1~2페이지로 실측해
비교하기 전에는 단정할 수 없다.**

### 3-3. 예상 난관

이 PDF 를 눈으로 본 결과 다음이 걸릴 것으로 본다.

1. **기울기** — 스캔이 미세하게 기울어져 있다. OCR 줄 좌표가 흔들리면 좌/우 칼럼 판정과
   `DEFAULT_ANCHOR_INDENT_TOL = 30.0` (들여쓰기 허용치)이 어긋난다. deskew 가 필요할 수 있다
2. **제본 그림자** — 오른쪽 스프링 자국이 크롭에 딸려 들어가면 여백 트림(`_WHITE_LEVEL = 250`)이
   무력화된다. extractor 의 `content_rect` 가 이걸 본문으로 오인할 수 있다
3. **번호 체계가 다르다** — 이 부교재는 `< 기 본 >` / `< 심 화 >` 섹션마다 번호가 **1부터
   다시 시작**한다. 한 페이지에 `1.` 이 두 번 나온다. 시험지용으로 만든 "페이지 내 번호는
   유일하다" 전제가 깨진다. 섹션 헤더를 인식하거나 (페이지, 칼럼, 순번) 으로 문항 키를
   바꿔야 한다 ← **이것이 가장 큰 설계 문제다**
4. **문항 크기 편차** — 심화 문항은 그림이 딸려 세로로 길다. 다음 앵커까지 자르는 현재 방식이
   그림을 잘라먹지는 않는지 확인이 필요하다

4번보다 3번이 먼저다. 번호가 중복되면 `problems` 테이블의 `PRIMARY KEY(node_id, no)` 자체가
성립하지 않는다.

## 4. 다음 단계 (착수한다면)

2. 섹션 중복 번호를 어떻게 다룰지 결정 (`problems` 스키마에 영향)
3. 결정 후 정식 스펙 작성 → 구현

지금 단계에서 "가능하다" 고 말할 수 있는 근거는 페이지 이미지가 충분히 선명하다는 것뿐이다.
OCR 이 이 조판에서 실제로 앵커를 잡아내는지는 **측정하지 않았다.**
