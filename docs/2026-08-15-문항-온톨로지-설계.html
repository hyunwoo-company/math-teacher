진단“조건 변형”이 안 되는 건 프롬프트 문제가 아니다

현재 변형 기능은 숫자 / 조건 / 숫자+조건 세 가지 모드를 제공한다. 이 중 조건 변형만 유독 결과가 나쁜 데에는 구조적 이유가 두 개 있다.

"condition": (
    "변형 방식: 수치의 규모는 원본과 비슷하게 유지하되, **조건·설정·상황(문맥)만** "

    "개념과 난이도는 그대로 두십시오."

㉮ 수학 문항에서 “조건”은 문제 그 자체다

숫자 변형은 잘 된다. 바꿀 대상(상수·계수·좌표)이 문법적으로 특정되기 때문이다. 반면 “조건”을 바꾸면 갈림길이 둘뿐이다 — 유형이 바뀌거나(원치 않음), 소재만 갈아끼운 껍데기 변형이 되거나(가치 없음). 지시문이 애매한 게 아니라 지시 대상이 애매하다.

㉯ “유형 유지”를 검증할 수단이 시스템에 없다

프롬프트가 “같은 유형·유사 난이도”라고 스무 번 말해도, ‘유형’이라는 것이 데이터로 존재하지 않는다. variants 테이블에도 text만 있고 유형 식별자가 없어, 생성물이 원본과 같은 유형인지 아무도 확인하지 않는다. LLM이 암묵적으로 잡고 암묵적으로 지키므로 표류한다.

그래서

온톨로지 도입은 “유사 문항 추천”이라는 신기능만 만드는 것이 아니다. 원본 태그를 생성기에 명시 입력으로 주고, 생성물을 다시 태깅해 태그가 일치하는지 자동 검증할 수 있게 되므로 기존 변형 기능의 결함 자체를 메운다.

시장 빈틈

콴다조교의 “AI 유사문제”는 DB 검색이 아니라 생성형이고, 안내문에 “최종 사용 전 수학적 오류 확인 필요”가 명시돼 있다. 즉 시장 1위도 검증된 실물 문항 추천은 하지 못하고 있다.

설계 1온톨로지 — RDF/OWL이 아니라 “얇은 앵커 + 두꺼운 유도층”

온톨로지라 하면 그래프 DB를 떠올리기 쉬운데, 필요한 건 그게 아니다. 다면 분류(faceted taxonomy)는 중첩이 아니라 가산적이라 조합 폭발 없이 다차원 필터가 된다. 4개 층으로 나눈다.

L0

커리큘럼 앵커 — 폐쇄형, 고정

2022 개정 교육과정 성취기준 코드. 중학교는 [9수01-01], 고등 공통수학1은 [10공수1-02-03] 형식이다. 공통수학1만 4영역 19개로 실측 확인했다.

장점 — 외부 표준이라 안정적이고, 선생님이 이미 쓰는 말이며, “2단원까지 출제” 같은 시험범위 필터에 직결된다. 한계 — 너무 굵다. 근과 계수의 관계 하나에 수백 문항이 들어간다.

L1

문제 유형 — 시스템이 스스로 키우는 층

“유사”의 실제 단위다. 한국 현장이 이미 쓰는 단위이기도 하다(문제집 유형 07: 근과 계수의 관계를 이용한 대칭식의 값).

중고 전과목이면 유형은 1,500~4,000개 규모다. 사람이 손으로 못 만든다. 그래서 미리 만들지 않고 문항이 들어올 때 자라게 한다 — 다음 절이 그 방법이다.

L2

풀이 전략 지문 — 이 앱의 구조적 우위

같은 유형이어도 학생이 실제로 하는 일이 다르면 유사하지 않다. solutions 테이블에 이미 문항별 풀이가 있으므로, 발문 표면이 아니라 풀이 단계에서 유사도를 잴 재료가 공짜로 있는 상태다.

L3

표면 속성 — 유사도가 아니라 사용자 다이얼

문항형식 · 배점 · 시각요소 · 맥락(순수/실생활) · 조건상자 유무 · 계산량 · 출처.

이 층이 “조건 변형”의 애매함을 직접 해소한다. 뜻이 불분명한 3택 대신, 무엇을 고정하고 무엇을 풀지를 명시적으로 고르게 한다.

설계 2유형 진술문 — 온톨로지를 자동으로 자라게 하는 장치

중고 전과목에서 유형 사전을 미리 손으로 만드는 것은 불가능하다. 그렇다고 순수 임베딩으로 가면 Prob2Vec의 75%에 갇힌다. 해법은 LLM이 각 문항을 정규화된 한 문장으로 환원하게 하고, 그 문장을 유형의 정체성으로 삼는 것이다.

유형 진술문(canonical statement) — 태깅 출력의 핵심 필드
"이차방정식의 두 근에 대한 대칭식의 값을,
 근을 직접 구하지 않고 근과 계수의 관계로 구한다."

이 한 문장이 네 가지 역할을 동시에 한다.

  • 임베딩 대상 — 원문이 아니라 이 문장을 임베딩한다. 이것이 Prob2Vec의 75%→96.88%를 만든 “추상화” 단계의 정체다.
  • 유형 노드의 이름이자 정의 — 별도로 유형 이름을 짓지 않아도 된다.
  • 사람이 읽고 검수 가능 — LLM F1이 0.62인 이상 검수 경로가 반드시 필요하다.
  • “LLM 위키”의 페이지 제목 — 유형 하나가 위키 문서 하나가 된다.

자라는 방식 — 온라인 군집화

확장성의 핵심 결정

관계는 문항↔문항이 아니라 문항→유형→유형이어야 한다. 문항 쌍 관계를 저장하면 N² 폭발한다(문항 1만 개면 5천만 쌍). 유형은 수천 개고 유형 간 관계는 손에 잡힌다. 문항 유사도는 유형을 경유해 계산하지, 저장하지 않는다.

유형 간에 저장할 관계 — “LLM 위키”의 실체

관계의미쓰임
same_type같은 유형유사 문항 추천의 주력
harder / easier같은 유형, 난이도 차단계별 처방
prerequisite선행 — 이 유형을 풀려면 저 유형을 알아야취약 단원 역추적
composes복합 — 유형 2개 이상이 결합4점 문항 대부분이 여기
same_trap같은 함정오답노트와 직결 · 차별화 지점

설계 3검색 — 3단, 단 3단째는 나중에

유사 문항 랭킹 파이프라인
1) 하드 필터   성취기준 일치(또는 인접) ∩ 시험범위 ∩ 학년

2) 가중 스코어  유형 일치         × 0.45
               풀이전략 코사인    × 0.25
               난이도 거리        × 0.15
               표면속성 일치      × 0.15   ← 사용자 다이얼이 이 가중치를 조절
               − 같은 시험지 중복 페널티 (MMR)

3) LLM 재순위   상위 20건 → 코퍼스 1,000건 넘기 전엔 생략

태그 기반을 임베딩 위에 두는 결정적 이유는 설명 가능성이다. 선생님에게 “근과 계수의 관계 + 대칭식 유형이 같고, 배점도 3점으로 같습니다”라고 말할 수 있어야 신뢰가 생긴다. 순수 임베딩은 이걸 못 한다.

난이도는 따로 다뤄야 한다

태그 중 LLM이 가장 못 맞히는 값이다. 절대 등급을 물으면 흔들린다.

  1. 1차 신호는 배점 — 이미 시험지에 찍혀 있고 출제자 본인이 매긴 값이다. 공짜이고 가장 정확하다.
  2. LLM에는 절대 등급 대신 쌍대 비교를 시킨다(“이 둘 중 어느 쪽이 어려운가”) → Elo / Bradley-Terry로 척도화. 절대 평정보다 훨씬 안정적이다.
  3. 장기적으로는 오답노트가 정답 — note_items에 쌓이는 “학생이 실제로 틀린 문항”이 진짜 난이도 신호다. 이 앱은 이미 그 데이터를 얻는 위치에 있다.

설계 4스키마

SQLite — 기존 storage.py 컨벤션에 맞춤
-- 통제 어휘. 유형 사전 자체.
CREATE TABLE problem_types (
  id          TEXT PRIMARY KEY,   -- 'T-0203-02'
  achievement TEXT NOT NULL,      -- '10공수1-02-03'
  statement   TEXT NOT NULL,      -- 유형 진술문 = 이름이자 정의
  includes    TEXT NOT NULL,
  excludes    TEXT NOT NULL,
  status      TEXT NOT NULL,      -- 'active' | 'proposed'  ← 자동 성장분
  created_at  TEXT NOT NULL
);

-- 문항 태그. (시험지, 문항) 당 1행. 재태깅은 덮어쓰기(variants 와 같은 규칙).
CREATE TABLE problem_tags (
  node_id           TEXT NOT NULL,
  no                INTEGER NOT NULL,
  achievements_json TEXT NOT NULL,  -- ["10공수1-02-03"]  복수 가능
  statement         TEXT NOT NULL,  -- 이 문항의 유형 진술문
  strategy_json     TEXT NOT NULL,  -- {steps:[], traps:[], step_count:n}
  facets_json       TEXT NOT NULL,  -- {format, points, visual, context, ...}
  difficulty        REAL NULL,      -- 배점 + 쌍대비교 Elo
  confidence        REAL NOT NULL,  -- 낮으면 사람 확인 큐
  evidence          TEXT NOT NULL,  -- 판단 근거(발문 인용). 검수용
  source            TEXT NOT NULL,  -- 'ai' | 'manual'
  created_at        TEXT NOT NULL,
  PRIMARY KEY (node_id, no)
);

-- 유형 역색인. json1 대신 조인 테이블(인덱스 활용).
CREATE TABLE problem_type_map (
  type_id TEXT NOT NULL, node_id TEXT NOT NULL, no INTEGER NOT NULL,
  PRIMARY KEY (type_id, node_id, no)
);
CREATE INDEX idx_type_map_problem ON problem_type_map(node_id, no);
파이프라인 순서

태깅 입력은 크롭 이미지 + problems.transcript + solutions.solution 3종 결합이 최선이다. 판독본과 풀이가 있는 문항은 태깅 품질이 크게 오르므로, 순서를 추출 → 텍스트화 → 풀이 → 태깅으로 두면 된다. 기존 jobs 큐에 kind='tag'를 얹으면 진행·중단 UI가 그대로 재사용된다.

리스크콜드스타트가 가장 큰 위험

현재 DB 실측: 파일 1개, 문항 22개, 풀이 2개. 추천이 성립하려면 유형당 최소 5~10문항이 필요하고, 유형 50개면 250~500문항 = 시험지 15~25장이 임계점이다.

  1. 온보딩에서 폴더 통째 업로드를 유도하고, 업로드 시 태깅을 자동 실행한다.
  2. 추천 결과가 비면 생성으로 폴백한다 — 그리고 생성물도 태깅해 코퍼스에 넣되 출처=AI생성으로 신뢰 등급을 구분한다.
  3. 실패를 정직하게 표시한다 — “이 유형의 다른 문항이 아직 없습니다 → 변형 문제를 만들까요?”
결론

추천 vs 생성이 아니라 “추천 우선 + 생성 폴백”이다. 추천은 수학 오류 0 · 조판 정상 · 출처 존재라는 압도적 이점이 있고, 생성은 코퍼스가 얇을 때의 안전망이다.

실행로드맵 — 각 단계가 단독으로 가치를 낸다

Phase 0

코드 없이 손태깅으로 검증

시험지 3~5장을 손으로 태깅해, 유형 진술문이 실제로 변별되는지 눈으로 확인한다.

여기서 안 갈리면 뒤가 전부 무너진다 — 반드시 먼저
Phase 1

태깅 job + 문항 태그 배지

problem_tags 테이블과 태깅 작업 큐를 붙이고, 문항 상세에 태그를 노출한다. 추천은 아직 없다.

시험지 성취기준 분포도 — 출제 균형 점검만으로 즉시 유용
Phase 2

같은 유형 문항 찾기

유형 조인 + 배점 근접만으로 SQL 검색. 임베딩 없음.

코퍼스가 작을 땐 이걸로 충분 — 리서치 근거 있음
Phase 3

풀이 전략 임베딩 + 가중 스코어 + 다이얼 UI

진술문 임베딩을 붙이고, 사용자가 “무엇을 고정할지” 고르는 UI를 만든다.

진짜 “유사 문항 추천”
Phase 4

변형 생성기를 온톨로지 위에 재구축

태그를 명시 입력으로 주고, 생성물을 재태깅해 원본 태그와 일치하는지 자동 검증한다. 불일치면 재생성.

“조건변형이 안 된다”의 직접 해법
Phase 5

오답노트로 난이도 보정 · 학생별 처방

실제 오답률로 난이도를 교정하고, 학생별 취약 유형에서 prerequisite를 역추적한다.

오답노트 기능이 여기서 자산으로 전환

하지 말 것

  • RDF/OWL 정식 온톨로지 — 필요한 표현력을 한참 초과한다. SQL 테이블로 충분하다.
  • 깊은 계층 지식그래프 — GraphRAG는 증분 갱신을 지원하지 않아 주기적 전체 재구축이 필요하다. 문항이 계속 추가되는 이 서비스와 맞지 않는다.
  • 자체 임베딩 모델 학습(MathBERT류 파인튜닝) — 데이터 22문항으로는 논외다.
  • 지식추적(DKT/BKT) — Phase 5 이후, 학생 응답이 수천 건 쌓인 뒤.
  • 성취기준만으로 유사 판정 — L1 유형 층 없이는 “근과 계수의 관계” 수백 문항이 전부 유사가 된다.

선행 과제과목 하드코딩 제거 — 그리고 프롬프트 캐시

이 서비스는 중·고등 수학 전반을 다뤄야 하는데, 현재 app/core/prompts.py가 고1 공통수학1로 하드코딩돼 있다. 단원 목록까지 프롬프트에 박혀 있어, 다른 과목 시험지를 올리면 풀이·변형·판독이 모두 잘못된 범위로 작동한다.

위치내용
prompts.py:26_SKILL_PERSONA_SCOPE — “고등학교 1학년 ‘공통수학1’(다항식, 나머지정리와 인수분해, …)”
prompts.py:157SOLVE — “고등학교 1학년 학생이 독자입니다”
prompts.py:194CHAT — “고등학교 1학년 ‘공통수학1’ 교과 범위 안에서”
prompts.py:269VARIANT — “교과 범위(공통수학1) 밖의 개념을 끌어오지 마십시오”
함께 고쳐야 하는 것 — 프롬프트 캐시

providers/apikey.py:113이 system 프롬프트에 cache_control을 건다. Anthropic 프롬프트 캐시는 접두사 일치이고 렌더 순서는 tools → system → messages다. 접두사의 1바이트만 달라도 그 뒤가 전부 무효화된다.

그런데 _SKILL_PERSONA_SCOPE는 system 프롬프트의 맨 첫 줄이다. 여기를 과목별로 바꾸면 캐시가 100% 미스가 된다 — 문항별 개별 호출이라 타격이 크다.

해법

system 프롬프트는 과목과 무관하게 완전히 고정하고, 과목·학년·시험범위 같은 가변 정보는 user 메시지로 내린다. messages는 system 뒤에 렌더되므로 system 캐시를 깨지 않는다. 즉 과목 하드코딩 제거와 캐시 최적화가 같은 한 번의 수정으로 해결된다.

참고 — docstring의 “프롬프트 캐시 최소 토큰 1024~2048”은 현재 기본 모델 claude-opus-5 기준 512 토큰으로 낮아졌다.

결정 대기지금 정해야 하는 것

  1. 유형 씨앗의 시작 범위 — 한 과목(공통수학1, 유형 40~60개)부터 검증할지, 처음부터 중1~고3 전체를 자동 유도에 맡길지.
  2. 코퍼스 확보 경로 — 손에 실제 시험지가 몇 장 있는지. Phase 2가 성립하려면 15~25장이 필요하다. 없으면 Phase 4(온톨로지 기반 변형)를 먼저 하는 순서 조정이 맞다.
  3. 기존 condition 변형 모드의 처분 — 유지할지, L3 facet 기반 다이얼로 대체하고 제거할지.
